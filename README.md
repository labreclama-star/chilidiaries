# ChiliDiaries — React + Vite

Миграция прототипа ChiliDiaries (vanilla HTML/CSS/JS) на React + Vite.
Дизайн, UX, структура страниц и вся функциональность сохранены as-is.

## Запуск

```bash
npm install
npm run dev
```

Откроется на http://localhost:5173

## Сборка

```bash
npm run build
npm run preview   # локально проверить собранный dist/
```

> ⚠️ Важно: сборка и установка зависимостей не выполнялись автоматически в среде,
> где готовился этот проект (нет доступа в интернет для npm-реестра). Каждый файл
> вручную проверен на синтаксическую корректность (`node --check` для `.js`,
> собственный скрипт проверки баланса скобок/тегов для `.jsx`), а все импорты/экспорты
> сверены между файлами программно — но реальный `npm run build` стоит запустить
> самостоятельно при первом запуске.

## Как посмотреть проект прямо сейчас (без npm install)

Помимо самого React-проекта, в этом ответе есть **`chilidiaries-preview.zip`** —
уже собранный статический билд (HTML+JS+CSS одним набором файлов, без Node.js
и npm на твоей стороне). Чтобы посмотреть:

1. Распакуй `chilidiaries-preview.zip`
2. Открой `index.html` в браузере (можно через `python3 -m http.server` в этой
   папке и зайти на `http://localhost:8000`, либо просто дважды кликнуть файл —
   при прямом открытии как `file://` работает всё, кроме клиентского роутинга
   при обновлении страницы на не-главном URL, так что для полноценной проверки
   лучше через локальный сервер)

Это не финальная прод-сборка (собрана обходным путём через esbuild и лёгкую
замену react-router-dom, без Vite и без npm — потому что в среде, где я работаю,
нет доступа в интернет для `npm install`), но это на 100% тот же исходный код
из `src/`, реально скомпилированный и проверенный в headless-браузере
(Playwright): я прогнал навигацию по всем разделам, лайки, подписки,
модалку входа, мобильную раскладку — без единой ошибки в консоли. По пути
это нашло и исправило один реальный баг (бейджи стадии/SHU на странице
дневника наезжали друг на друга — CSS-правило было привязано к другому
классу контейнера) — исправление уже внесено в `src/index.css` в основном
проекте.

Настоящая прод-сборка (`npm run build` через Vite) даст тот же результат,
но чище и оптимизированнее — сделай её у себя при первой возможности.

## Редизайн (визуальный апдейт)

Поверх исходной миграции сделан визуальный редизайн по референсам (dark/premium/
editorial, «земля + перец + огонь + данные + сообщество»), без переписывания
информационной архитектуры и без потери функций:

- **Дизайн-система**: в `index.css` поверх существующей палитры добавлены
  семантические алиасы (`--background`, `--surface`, `--surface-hover`, `--border`,
  `--text`, `--text-muted`, `--chili-orange`, `--chili-red`, `--leaf-accent`,
  шкалы spacing/radius/shadows) — старые переменные (`--soil-*`, `--ember` и т.д.)
  не удалялись, чтобы ничего не сломать, но теперь весь проект можно перекрасить
  из одной точки.
- **Новые переиспользуемые компоненты**: `StatsCard` (блок «твой показатель vs
  среднее по сообществу» с дельтой), `ProgressBar` (универсальный прогресс-бар),
  `HeatIndicator` (компактный индикатор остроты для карточек), `AchievementBadges`
  (коллекционные бейджи гровера — «Первый гров», «100+ подписчиков» и т.д.,
  выведены из уже существующих полей `diaries`/`followers`, никаких новых сущностей),
  `FilterBar`/`Badge` (см. предыдущий этап), `Reveal` (лёгкая scroll-in анимация
  на IntersectionObserver, без тяжёлых библиотек).
- **DiaryCard** стала гибридом соцсети/дневника/дашборда: день грова прямо в
  бейдже стадии, сравнение остроты (SHU) с средним по сорту среди других
  дневников (реальный расчёт по существующим данным, не выдумано).
- **DiaryDetail**: добавлены `StatsCard`-сравнение и бейджи достижений гровера
  в сайдбаре.
- **Hero**: переписан на редакционный многострочный H1 («Веди свой гров. /
  Сравнивай. / Становись острее.»), в качестве фона карточки шкалы Сковилла
  используется реальное загруженное фото Carolina Reaper с тёмным overlay —
  кинематографичнее плоского градиента.
- **Микро-анимации**: hover-zoom фото карточек, более выраженный glow на
  primary-кнопках, лёгкое появление секций при скролле на главной.

Все существующие данные, страницы, маршруты, авторизация, мастер создания
дневника и mock-слой — без изменений по функциональности.

- **Профиль гровера** (`/growers/:id`) — новая страница: аватар, локация, био, статистика
  (StatsCard: дневников, подписчиков, отчётов, лайков), полный набор бейджей достижений,
  любимые сорта (выведены из его дневников), сетка всех его дневников. Карточки гроверов
  и клик по гроверу в дневнике теперь ведут туда (раньше это была заглушка-тост).
- **Header** уплотнён: меньше вертикальный паддинг, добавлена мягкая тень глубины вместо
  плоской границы — премиальнее на фоне контента при скролле.

## Публикация (деплой)

Проект — обычный статический SPA-билд (`npm run build` → папка `dist/`), поэтому
подходит любой статический хостинг. Конфиги уже добавлены:

- **Netlify** — `netlify.toml` в корне (билд-команда, редиректы для клиентского роутинга).
  Проще всего: зайти на [app.netlify.com/drop](https://app.netlify.com/drop) и перетащить
  папку `dist/` после `npm run build` — ссылка будет готова за секунды. Либо подключить
  репозиторий — Netlify сам подхватит `netlify.toml`.
- **Vercel** — `vercel.json` в корне (rewrite всех путей на `index.html`, чтобы прямые
  ссылки вида `/diaries/d_1` не отдавали 404 при обновлении страницы). Импортируешь
  репозиторий на vercel.com — настройки подхватятся автоматически (Vite определяется сам).
- **GitHub Pages / другой статический хостинг без встроенных rewrite-правил** — тоже
  сработает, но нужно либо переключить `BrowserRouter` на `HashRouter` в `src/main.jsx`,
  либо настроить fallback на `index.html` на уровне хостинга самостоятельно — без этого
  прямые ссылки на внутренние страницы (не с главной) будут давать 404 при обновлении.

Файл `public/_redirects` — дублирующий Netlify-редирект на случай, если `netlify.toml`
не подхватится автоматически (например, при ручной загрузке `dist/`).

## Структура

```
src/
  components/     — переиспользуемые UI-компоненты (карточки, модалки, шапка, сайдбар...)
  pages/          — 13 страниц + NotFound (404), по одной на каждый маршрут
  data/           — статические mock-данные (сорта, гроверы, дневники, рецепты, статьи...)
  services/       — тонкий слой доступа к данным, уже готовый под замену на Supabase
  context/        — AppContext.jsx — глобальное состояние приложения (замена старого STATE)
  utils/          — чистые хелперы (расчёт цвета остроты, генерация отчётов и т.д.)
  App.jsx         — маршруты + общий layout
  main.jsx        — точка входа
  index.css       — все стили проекта (перенесены без изменений)
```

Из архитектурного примера в ТЗ отдельно вынесены и переиспользуются везде:
`FilterBar.jsx` (+ `FilterChip`) — шапка фильтров на страницах Дневников/Сортов/Рецептов,
`Badge.jsx` — единая карточка-бейдж (стадия/SHU/тег), раньше повторявшаяся как инлайн-разметка
в каждой карточке по отдельности.

## Что работает на mock-данных (готово к переезду на Supabase)

Все данные (`src/data/*.js`) сейчас — статические JS-массивы в памяти. Любые изменения
(лайки, подписки, новые дневники/сорта/рецепты/статьи, комментарии) живут только в
React state на клиенте и сбрасываются при перезагрузке страницы.

Слой `src/services/*.js` уже сейчас имеет асинхронные сигнатуры (`async function fetchX()`,
т.е. возвращает `Promise`), как будто внутри уже настоящий сетевой запрос — это сделано
специально, чтобы подключение Supabase не потребовало трогать компоненты вообще.

## Что нужно сделать для подключения Supabase (следующий этап)

1. Создать таблицы: `growers`, `varieties`, `diaries`, `diary_weeks`, `diary_comments`,
   `recipes`, `blog_posts` (+ связи по `grower_id`/`variety_id`/`diary_id`).
2. В каждом файле `src/services/*.js` заменить тело функций `fetchInitial*()` на реальные
   запросы через `supabase.from('table').select(...)` — сигнатуры функций менять не нужно,
   компоненты и AppContext их не почувствуют.
3. `createDiaryFromWizard`, `createVarietyFromForm`, `createRecipeFromForm`, `createPostFromForm`,
   `createWeekReport` в services — заменить локальное создание объекта на `supabase.from(...).insert(...)`.
4. `src/services/authService.js` — заменить `login`/`signup`/`logout` на
   `supabase.auth.signInWithPassword`/`supabase.auth.signUp`/`supabase.auth.signOut`.
   Сигнатуры (`{identifier, password}` / `{name, email, password}`) уже совместимы по духу.
5. Для загруженных фото (сейчас — base64 data URL в памяти) — переключить на
   `supabase.storage.from('photos').upload(...)` и хранить получившийся URL вместо data URL.
6. В `AppContext.jsx` замены мутаций `setDiaries(prev => ...)` и т.п. на комбинацию
   локального optimistic-update + реального запроса через сервис — сама структура
   контекста менять не придётся, так как вся мутация уже проходит через отдельные
   функции (`toggleLikeDiary`, `createDiary`, `addComment`, ...), а не разбросана по компонентам.
7. Добавить сессию (`supabase.auth.onAuthStateChange`) вместо ручного `currentUser` в state.

Авторизация специально не «зашита» внутрь компонентов — `AuthModal.jsx` работает только
через `login()`/`signup()` из контекста, поэтому замена реализации внутри `authService.js`
не потребует правок в UI.

## Админка

В проекте есть встроенная админ-панель для управления всем контентом без правки кода.
Она не переиспользует Supabase-миграцию выше "как есть" — если будете переводить проект
на реальный бэкенд, админ-мутации (`admin*` в AppContext) тоже надо будет переключить на
реальные запросы по той же схеме, что описана в разделе выше.

### Как войти

1. На сайте открой окно входа (иконка профиля / «Войти»).
2. Логин: `admin`, пароль: `ChiliAdmin2026` (задан константой `ADMIN_PASSWORD` в
   `src/services/authService.js` — при желании поменяй значение прямо там).
3. После входа перейди на `/admin` (прямой переход по URL — отдельной кнопки в шапке
   сайта намеренно нет, чтобы не путать обычных пользователей).
4. Любой другой пользователь получит тост «Доступ запрещён» и редирект на `/`;
   без входа `/admin` открывает окно авторизации.

| Экспорт/Импорт | `/admin/data` | скачать/загрузить JSON со всеми данными, сброс к сид-данным |

### Хранение данных

Все изменения синхронизируются в `localStorage` под ключом `chilidiaries_state_v1`
(см. `src/services/persistenceService.js`) при каждом изменении контента. При следующей
загрузке сайта состояние читается из localStorage вместо сид-данных из `src/data/*.js`.
Если сохранённые данные повреждены или относятся к старой версии формата — приложение
тихо откатывается на сид-данные, а не падает.

**Сбросить всё к исходному демо-контенту:** `/admin/data` → «Сбросить к сид-данным»,
либо вручную `localStorage.removeItem('chilidiaries_state_v1')` в консоли браузера
и перезагрузка страницы.

### Известные упрощения (сознательно оставлены за рамками)

- Тумблеры «показывать Вопросы/Ленту» скрывают эти пункты в Sidebar и в шторке
  «Ещё» (`MoreSheetModal`), но не блокируют прямой переход по URL `/questions` или
  `/feed` — это админ-панель для контент-менеджмента, а не система прав доступа
  к роутам.
- «Отклонённые» статьи блога (`status: 'rejected'`) хранятся вместе с остальными и
  просто не показываются в публичном каталоге — отдельного архива для них нет.
- Участники конкурса, добавленные через админку (`participantIds`), не связаны с
  персональной кнопкой «Участвовать» на публичной странице (она использует свой
  сессионный `joinedContestIds`) — это два независимых списка, как и задумано
  в Этапе 9 (ручное управление отдельно от самостоятельного участия).
