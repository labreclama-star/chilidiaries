## ⚡ Краткая сводка (обновлено после сессии с доп. фичами и мобильными фиксами)

### 1. Суть проекта
ChiliDiaries — соцсеть/веб-платформа для любителей выращивания острого
перца (чили): личные дневники выращивания по неделям, каталог сортов с
рейтингами, гроверы (профили), рецепты, блог, конкурсы, Q&A, лидерборд.
Сейчас — фронтенд-прототип на моковых данных (без бэкенда), но с полностью
рабочей бизнес-логикой на клиенте (лайки, подписки, комментарии, голосования
и т.д. — всё через React state, ничего не сохраняется между перезагрузками).

### 2. Ключевые архитектурные решения
- **Стек:** React 18.3 + Vite 5 + `react-router-dom` v6. Чистый JS (не TS).
  Ванильный CSS (`src/index.css`, ~900 строк) — без Tailwind/CSS-modules,
  переменные через CSS custom properties (`--ember`, `--habanero` и т.п.,
  тема "жгучий перец/подпалённая земля").
- **Состояние:** один большой `context/AppContext.jsx` (React Context +
  useState/useCallback), никакого Redux/Zustand. Все данные — в памяти,
  инициализируются из `src/data/*.js` (сиды) через `src/services/*` при
  старте. **Персистентности нет вообще** (ни localStorage, ни бэкенда) —
  это осознанное решение, пока проект — прототип.
- **Модалки:** один компонент `components/Modal.jsx`, всё управляется через
  `activeModal` + `modalPayload` в контексте (`openModal(name, payload)` /
  `closeModal()`). На мобильных все модалки автоматически становятся
  bottom-sheet (нижняя шторка) через CSS.
- **Мобильный шелл:** единый брейкпоинт **768px** (мобильный режим:
  сайдбар скрыт → нижняя таб-панель + FAB + шторка «Ещё») и **480px**
  (сверхмалые экраны, минимальные отступы). Все hover-эффекты вынесены в
  `@media (hover:hover) and (pointer:fine)` (не залипают на тач-устройствах).
- **Структура:** `src/{App.jsx, main.jsx, index.css, context/, data/,
  services/, utils/, components/ (51 файл), pages/ (20 файлов)}`.
  `services/` — прослойка "как бы fetch" (сегодня читает из `data/`, завтра
  можно заменить на реальные API-вызовы, не трогая компоненты).
- **Офлайн-верификация:** в песочнице нет доступа к npm-registry, поэтому
  вместо `npm run build` весь код прогоняется через локально доступный
  `esbuild` (синтаксис + полная сборка бандла с react/react-dom/
  react-router-dom как external) — ловит 95% реальных ошибок, но не
  заменяет настоящую сборку у пользователя перед деплоем.

### 6. Открытые вопросы / нерешённое
- **Нет бэкенда и персистентности** — весь прогресс исчезает при
  перезагрузке страницы. Не поднималось явно пользователем как проблема,
  но для фич вроде "напоминаний" и "приватных дневников" это станет
  ощутимым ограничением демо (напоминание, которое не переживает reload,
  бесполезно) — стоит явно обсудить с пользователем, нужен ли localStorage
  хотя бы как временное решение, или это по-прежнему чисто витринный прототип.
- **UI для сравнения гровов** не спроектирован вообще — нужно решить с
  пользователем формат (сплит-скрин/оверлей-график/таблица) до кодинга.
- **"Как в GrowDiaries"** — пользователь ссылался на стороннее приложение
  как референс; не стал впрямую копировать его конкретный UI (риск
  выглядеть как прямое заимствование чужого дизайна), сделал общие
  нативные паттерны (bottom-sheet, tap-feedback, letterbox-фото). Если
  нужно точнее попасть в референс — стоит явно спросить, что конкретно
  из GrowDiaries нравится (конкретные экраны/паттерны), а не пытаться
  угадывать по памяти.
- **Настоящая сборка не прогонялась** — только offline-эмуляция через
  esbuild (ловит синтаксис/битые импорты, но не версии зависимостей,
  Vite/PostCSS-специфику, визуальные баги на реальных устройствах).

## 1. Суть проекта (расширенная версия)

**ChiliDiaries** — социальная платформа для гроверов острого перца
(концептуально близко к growdiaries.com, но про chili, а не каннабис).

Что делает пользователь на сайте:
- ведёт пошаговый **дневник выращивания** (от рассады до урожая) с фото-отчётами;
- сравнивает жгучие **сорта перца** (капсаицин, аромат, рейтинг);
- публикует и читает **рецепты** и статьи **блога**;
- задаёт и отвечает на **вопросы** (Q&A про проблемы с растениями);
- участвует в **конкурсах**, следит за **рейтингом гроверов**;
- подписывается на других гроверов и дневники, получает уведомления и **бейджи-достижения**.

Пройденные этапы:
1. Прототип на чистом HTML/CSS/JS — done.
2. Миграция на **React + Vite + JavaScript** (без TypeScript) — done.
3. Визуальный редизайн (dark/premium/editorial стиль) — done.
4. Несколько больших пакетов доработок функциональности — done (детали в §3).
5. **Backend на Supabase** — не начат, отложен по просьбе пользователя в пользу фронтенда (см. §5 и §6).

## 2. Ключевые архитектурные решения

- **Стек:** React 18/19 + Vite + JavaScript (без TS, без Next.js). Роутинг — `react-router-dom` v6.
- **State management:** без Redux/Zustand — один большой `src/context/AppContext.jsx` (React Context + `useState`/`useCallback`), единый источник правды для всего приложения.
- **Данные:** полностью mock — статические JS-массивы в `src/data/*.js`, живут в памяти клиента (сбрасываются при перезагрузке страницы). Спроектировано специально так, чтобы позже подменить на Supabase **без переписывания компонентов**.
- **Слой `src/services/*.js`:** тонкие `async`-обёртки (`fetchInitialX()`, `createXFromForm()`) — уже сегодня выглядят как будущие Supabase-запросы. Именно сюда нужно будет подставлять `supabase.from(...)`, когда дойдём до бэкенда.
- **Стили:** один файл `src/index.css`, чистый CSS с design-токенами (`--soil-*`, `--ember`, `--habanero`, `--leaf` и т.д.). Тёмная/светлая тема через `[data-theme="light"]`.
- **Файловая структура:**
  ```
  src/
    pages/          20 страниц (по одной на маршрут) + NotFound
    components/     44 переиспользуемых компонента
    context/AppContext.jsx   — вся бизнес-логика и состояние приложения
    utils/helpers.js         — ~35 чистых функций: расчёты, форматирование, рейтинги
    services/*.js   (8 файлов) — mock-слой данных, будущая точка интеграции с Supabase
    data/*.js       (11 файлов) — сид-данные (сорта, гроверы, дневники, рецепты, блог, конкурсы, вопросы, свет, удобрения)
    index.css                — вся стилистика проекта
  ```

### Модель данных дневника (важно!)
`diary.weeks` — массив отчётов (имя поля историческое, по смыслу это "reports"), каждый объект:
```js
{ n, day, title, stage, date, note, temp, hum, photos: [] }
```
- `diary.reportInterval`: `'daily' | 'every3' | 'weekly' | 'custom'` — выбирается при создании, не enforced, просто подсказка.
- `diary.stage`: одна из `DIARY_STAGES` = `['Рассада','Вегетация','Цветение','Плодоношение','Собран урожай']`. Выбирается при создании дневника, **владелец может менять её позже** прямо на странице дневника (`updateDiaryStage`). Переход в `'Собран урожай'` = «закрытие сезона» → тост + бейдж.
- `diary.coverPhoto` — фото, которое загрузил сам гровер. **Приоритетно** над фото сорта везде, где показывается превью дневника (см. `diaryMediaStyle()` в helpers.js — отличать от `podMediaStyle()`, который используется только для карточек сортов/рецептов без диария).
- **Важно:** нигде не используется "живой" расчёт `Date.now() - startDate` для бейджей на фото — вместо этого `latestReportDay(diary)` (день последнего реального отчёта). Это специально задокументировано в коде — раньше был баг с абсурдными числами дней.

### Формула рейтинга гроверов (Leaderboard)
```
score = diaries×10 + followers×1 + totalLikes×2 + totalWeeks(reports)×3 + unlockedBadges×15
```
См. `growerScore()` / `rankGrowers()` в `helpers.js`.

### Бейджи гровера (`growerBadges()` в helpers.js)
🌱 Первый гров · 📓 5 дневников · 🔥 100+ подписчиков · 🏆 Топ-гровер · 🌶️ Коллекционер сортов · 🥉/🥈/🥇 10/20/30 сортов выращено · 🎖️ **Закрытие сезона** (≥1 дневник со stage `'Собран урожай'`).

### Модель подписок (важное ограничение текущей mock-архитектуры)
`grower._followed` — булев флаг "подписан ли ТЕКУЩИЙ пользователь на этого гровера". Это **глобальный** флаг в рамках одной сессии (однопользовательская модель), а не таблица связей. На своей странице профиля видно «Мои подписки» = `growers.filter(g => g._followed)`. **При переходе на Supabase это должно стать таблицей `follows(follower_id, followed_id)`.** Подписаться на самого себя нельзя — защита и в `toggleFollowGrower()` (контекст), и на уровне UI (кнопка скрыта/задизейблена).

### Рейтинги сортов
`variety.rating`, `variety.capsaicinRating`, `variety.aromaRating` — сгенерированы один раз детерминированной формулой в `src/data/varieties.js` (не случайны при каждом рендере). Для сортов, добавленных пользователями — `null` до появления реальной системы голосования.

### Q&A (вопросы)
`question`: `{ id, growerId, diaryId (nullable), text, photo, stage, topic, status: 'open'|'solved', likes, liked, createdAt, updatedAt, answers: [] }`. Стадии — свой набор `QUESTION_STAGES` (Прорастание/Вегетация/Цветение/Плодоношение/Харвест, чуть иные названия, чем у `DIARY_STAGES`, — это осознанно, не баг). Сортировка ленты — по `updatedAt` (последний ответ поднимает вопрос наверх).

## 6. Открытые вопросы / известные ограничения

1. **Нет доступа в интернет в рабочей среде разработки** → `npm install`
   ни разу не запускался по-настоящему в этой среде. Вместо этого код
   проверяется через `node --check`, сверку импортов/экспортов, и — самое
   важное — реальный рендеринг: сборка через `esbuild` напрямую (в системе
   глобально установлены `react`/`react-dom`) с самодельным mini-роутером
   (заменяет `react-router-dom` только для офлайн-превью) + прогон в headless
   Chromium через Playwright. Это не настоящая prod-сборка (Vite не
   используется), но на ней реально находились и чинились баги.
   **Вывод: пользователю всё равно нужно самому один раз прогнать
   `npm install && npm run build`**, чтобы получить каноничную сборку и
   убедиться, что всё совпадает с офлайн-превью.
2. **Мок-авторизация не связывает одноимённых пользователей** — вход под
   именем существующего сид-гровера (например «ChiliKrot») создаёт НОВОГО
   независимого гровера (`u_ChiliKrot`), а не «входит» в существующего
   персонажа. Ожидаемо для demo-auth, решится реальным Supabase Auth.
3. **Уведомления о чужом дневнике нельзя полностью продемонстрировать** в
   однопользовательской сессии — логика в коде корректна (сработает с
   реальным multi-user backend), но живой тест «другой пользователь
   опубликовал отчёт → я получил уведомление» невозможен без Supabase.
4. **Поле `diary.weeks`** осталось историческим именем (по смыслу это уже
   "reports"/отчёты) — не переименовано осознанно, чтобы не плодить риск
   поломок массовым рефакторингом. Если будет мешать при проектировании
   Supabase-схемы — переименовать одним точечным проходом.
5. **`_followed` — не таблица, а глобальный флаг** (см. §2) — предупреждён
   в TODO по Supabase выше, но стоит держать в голове при любых будущих
   доработках подписок на фронтенде тоже (например, если добавлять
   multi-user demo-режим до реального бэкенда).

  (`on_auth_user_created`), автообновление `updated_at`, автоинкремент
  `likes_count` через триггеры на таблице `likes`, плюс рассылка
  `notifications` подписчикам дневника при новом отчёте (в моке это делалось
  только для одного текущего пользователя сессии — здесь по-настоящему, для
  всех подписчиков).
- `0005_seed_dev.sql` — синтетические dev-данные (12 гроверов, 14 сортов,
  12 дневников с отчётами, рецепты, статьи, вопросы/ответы, конкурсы,
  лампы/удобрения и т.д.) для проверки схемы на чистом Supabase-проекте.
  **Только для dev** — вставляет напрямую в `auth.users` с плейсхолдер-паролем.

### Этап 6 — скрипт-мигратор: `scripts/migrate-seed-to-supabase.mjs`
Node ESM-скрипт, который (в отличие от 0005) переносит ИМЕННО текущие
`src/data/*.js` — читает их через динамический `import()`, трансформирует
под схему (`weeks` → `diary_reports`, `photos[]` → `diary_photos`, slug из
`title`, даты в ISO, UI-поля вроде `_followed` отбрасывает) и заливает в
Supabase через `@supabase/supabase-js` пачками, `upsert` по id.
Идемпотентен: growers/profiles используют локальный кэш-файл
`scripts/.migration-id-map.json` (мок-id → `auth.users.id`, т.к. Supabase
Admin API не гарантирует свой uuid для нового юзера на всех версиях),
остальные сущности — детерминированный uuid v5 из мок-id (повторный запуск
просто обновляет те же строки). Пакет `@supabase/supabase-js` НЕ
устанавливался (нужно подтверждение) — see комментарий в начале файла.
Дата-луп протестирован (`node --check` + прогон `loadMockData()`-логики
против реальных `src/data/*.js`) — 11 growers, 196 varieties, 14 diaries и
т.д. читаются корректно.
